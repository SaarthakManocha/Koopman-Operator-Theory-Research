# Additional experiments (20 October 2026)

All run on the same 2-vCPU Intel VM (Linux 6.18, EEVDF), as root, with nothing else running.
Every number below is regenerated by the script named next to it.

## 1. Closed loop: a burst predictor steering the real Linux scheduler

**Idea.** Since kernel 6.12, EEVDF lets each task request its own time-slice length
(`sched_setattr`, field `sched_runtime`). A task with a shorter slice gets an earlier
virtual deadline, so it is served sooner after waking. Setting each task's slice to its
*predicted next CPU burst* is SJF expressed inside the stock Linux scheduler: no kernel
patch, no custom scheduler class.

**Set-up** (`closedloop/`):
- `task.c`: request tasks wake on a fixed period (15–25 ms) and do one CPU burst each,
  with lengths from a two-regime log-AR(1) process (short ≈ 0.3 ms, long ≈ 4 ms,
  regime switches with probability 0.05). Each request logs deadline, wake and finish.
  Separate CPU hogs spin and count the CPU milliseconds they obtain.
- `agent.py`: a user-space agent that polls `/proc/<pid>/schedstat` and `/status` every
  10 ms. It extracts bursts (CPU time between voluntary switches), predicts the next one,
  and sets slice = clamp(prediction, 0.1 ms, default slice). It only ever shortens slices.
- Policies:
  - stock Linux;
  - all tasks 0.1 ms;
  - hand-labelled (request tasks 0.1 ms);
  - EWMA agent;
  - Koopman agent (log-EDMD, 3 lags, refit every 20 bursts on the last 300);
  - both agents with a conformal margin (slice = prediction × exp(q), with q the 90th
    percentile of each task's recent log-errors);
  - oracle (the task sets its slice to its true next burst);
  - oracle with slice = 2 × burst.
- Paired design: every repetition runs every policy with the same random seeds, in
  shuffled order. 1 CPU (3 hogs + 4 request tasks, 8 repetitions × 20 s) and 2 CPUs
  (6 hogs + 8 request tasks, 6 × 20 s). That is 3,500 and 7,100 requests per run.
- Validation: each request task's own CPU accounting agrees with `/proc/<pid>/schedstat`
  within 0.6–0.9% (median per policy).

**Results.** Mean response time of short requests (< 1 ms of CPU), from
`closedloop/analyse_closedloop.py`:

| policy | 1 CPU | vs stock | 2 CPUs | vs stock |
|---|---|---|---|---|
| stock Linux | 2.14 ms | – | 2.22 ms | – |
| hand-labelled short slice | 2.07 | −3% | 2.17 | −2% |
| EWMA agent | 1.52 | −29% | 1.58 | −29% |
| **Koopman agent** | **1.48** | **−31%** | **1.59** | **−28%** |
| EWMA + conformal margin | 1.39 | −35% | 1.49 | −33% |
| Koopman + conformal margin | 1.71 | −20% | 1.76 | −21% |
| oracle, slice = burst | 2.20 | +3% | 2.29 | +3% |
| oracle, slice = 2 × burst | 1.16 | −46% | 1.19 | −46% |

- **Both predictors work.** Each beats stock Linux in every paired repetition (8/8 and
  6/6; Wilcoxon p = 0.008 and 0.03).
- **Koopman vs EWMA is a tie.** Koopman is 2.6% lower on 1 CPU (7/8 repetitions,
  p = 0.016) and equal on 2 CPUs (p = 0.44).
- **Slice size matters more than accuracy.** A slice exactly equal to the burst is no
  better than stock. The burst slightly overruns its slice, and the task is pushed back
  behind the hogs. Twice the burst gives −46%. The predictors work because their errors
  leave some margin.
  - The conformal margin helps EWMA (to −35%).
  - It hurts Koopman (−20%). Koopman's log-scale errors are wider, so its slices grow too
    long and lose their early deadline.
- **Hand labelling and 0.1 ms slices for everyone do not help.** They cut wake-up latency
  but chop every burst into 0.1 ms pieces (7–10× more context switches).
- **Cost:**
  - Long requests are 4–7% slower: the usual SJF trade-off. Mean response over all
    requests changes by +0.5 to +4%.
  - CPU hogs lose 3–7% of their CPU time. That loss equals the agent's own CPU time
    almost exactly (for example 0.57 s lost vs 0.60 s used by the Koopman agent), so it
    is the cost of a Python agent polling `/proc`. See section 4 for the cost in C.

## 2. Real programs instead of synthetic loops

**Set-up** (`kit/real_programs.py`; 3 captures × 60 s, both CPUs). Running at the same time:
- Redis 7 server driven by a paced client (GET/SET with occasional LRANGE/SORT);
- Node.js 22 HTTP server with light and heavy JSON endpoints in phases;
- SQLite 3.45 queries of mixed size;
- ffmpeg real-time H.264 encoding (all encoder threads);
- the load generators themselves;
- background: a parallel gcc build and xz compression, untracked.

One SCHED_IDLE spinner per CPU keeps cores out of the idle path. Without it, this VM's
kernel loses switch events. In a 15 s test without the spinners there were 1,639 orphan
switch-outs; with them there were 186 across all three 60 s captures, out of 310,000
timeslices.

**Validation** (36 threads with ≥ 60 bursts):
- CPU time within 1.8% (median) of `/proc/<tid>/schedstat`;
- wait time within 1.5% (median);
- 28/36 threads within 5%. The outliers are ffmpeg helper threads that run about 12 µs
  per slice, where a few µs of tracepoint overhead is a large fraction.

**Burst prediction** (same methods and 80/20 split as the main study;
`src/real_programs_analysis.py`). Ratio of MAE to the textbook EWMA, below 1 is better:

| method | threads better than EWMA | median ratio | sign test |
|---|---|---|---|
| **log-EDMD (Koopman)** | **32/36** | **0.71** | p = 2×10⁻⁶ |
| poly-EDMD (Koopman) | 35/36 | 0.81 | p = 1×10⁻⁹ |
| linear EDMD | 29/36 | 0.82 | p = 3×10⁻⁴ |
| gradient boosting | 34/36 | 0.79 | p = 2×10⁻⁸ |
| EWMA, tuned α | 29/36 | 0.94 | p = 3×10⁻⁴ |
| last value | 0/36 | 1.21 | – |

By program, log-EDMD's median ratio:

| Redis | SQLite | Node.js | ffmpeg | load generators |
|---|---|---|---|---|
| 0.55 | 0.56 | 0.85 | 0.74 | 0.73 |

On real programs, Koopman predictors beat the textbook estimator more clearly than on
the synthetic I/O jobs (median 0.71 against 0.86). Log-EDMD is the best method for
Redis, SQLite, Node.js and the load generators. Poly-EDMD and gradient boosting are best
for ffmpeg.

## 3. Koopman eigenvalues as a process fingerprint

1,484 windows of 150 bursts across five programs. Log-EDMD is fitted per window, and a
random forest classifies which program the window came from (leave-one-capture-out
cross-validation):

| features | balanced accuracy (chance 0.20) |
|---|---|
| eigenvalues only (7 numbers) | 0.76 |
| simple burst statistics (log mean, log spread, lag-1 autocorrelation) | 0.998 |
| both | 0.997 |

The spectrum alone identifies the program at 3.8× chance, with readable signatures:
- SQLite has purely real eigenvalues (|Im λ| = 0), meaning no oscillation;
- the load generators have the slowest mode (|λ₁| = 0.87);
- Node.js and Redis decay fastest (|λ₁| ≈ 0.45).

However, simple statistics are better. This is a descriptive result, not a classification
method.

## 4. Prediction intervals and cost

**Split conformal intervals** (`src/conformal_cost.py`; 60 processes from the validated
captures and Trace 3; fit 60% / calibrate 20% / test 20%; target 90%):

| class | method | median coverage | median width (× prediction) |
|---|---|---|---|
| I/O | log-EDMD | 0.90 | 5.7 |
| I/O | EWMA | 0.91 | 8.3 |
| phased | log-EDMD | 0.93 | 1.29 |
| phased | EWMA | 0.93 | 1.17 |

Coverage holds at the target. Koopman intervals are narrower in 34/60 series (median
width ratio 0.84), most clearly for I/O.

**Cost of one prediction:**

| implementation | operation | time |
|---|---|---|
| C, -O2 | predict next burst (3-lag operator) | 5.6 ns |
| C, -O2 | online recursive least-squares update | 29 ns |
| Python/numpy (used in the agent) | predict | 8.2 µs |
| Python/numpy (used in the agent) | refit on 300 bursts | 41 µs |

At about 35 ns per burst, a Koopman predictor costs less than a context switch (about
1–2 µs), so it would fit inside a sched_ext policy or the kernel itself.
